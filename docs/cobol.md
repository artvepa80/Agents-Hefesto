# COBOL analyzer

Moved from the README. All COBOL rules are free; no license is needed.

- **Source format:** a `>>SOURCE FORMAT IS FREE`/`FIXED` directive (or `$SET SOURCEFORMAT(...)`) in the first 50 lines decides the format. Without one, free format is inferred when a division header (or, in a copybook, a level-01/77 entry) starts before column 8; otherwise fixed format (columns 7-72) is assumed. The inference is a heuristic, so declare the directive if in doubt; the files read as free format this way are listed under **Notes** in the text report and in `meta.cobol_format_notices` (JSON).
- **COBOL004 (REDEFINES)** flags a `REDEFINES` only when one side holds packed (`COMP-3`), binary, float, pointer or signed numeric data and the two layouts differ (for example `PIC X(12)` over `PIC S9(10)V99`). Plain `PIC X`/unsigned display overlays, CICS BMS symbolic maps (and program overlays of a BMS input map, such as CardDemo's `01 FILLER REDEFINES CTRTLIAI`) the byte view of a binary integer (`PIC 9(4) BINARY` or `PIC S9(4) COMP` redefined as `PIC X` bytes of exactly its storage size, as CardDemo does to decode a VSAM file status), a signed zoned number split into digit groups with the sign on the last group (`PIC S9(10)` as `9(9)` + `S9`), a pointer viewed as one address-sized field (`USAGE POINTER` as `PIC X(4)`/`X(8)` or an unsigned 4- or 8-byte binary), and a table of constants redefined as an `OCCURS` table with the same layout per entry are skipped; a size mismatch, a SIGN clause, a signed or display view of a pointer, or a different per-entry layout is still flagged. Overlays whose bytes depend on the platform go to COBOL016 instead. Binary usages without a PIC (`BINARY-CHAR`, `BINARY-SHORT`, `BINARY-LONG`, `BINARY-LONG-LONG`, `BINARY-DOUBLE`, signed or unsigned) count as binary, with fixed sizes of 1, 2, 4, 8 and 8 bytes. **COBOL016 (platform-dependent REDEFINES, MEDIUM)** flags three overlays that read differently on z/OS and on x86 (GnuCOBOL, Micro Focus), each with its own message and suggestion: `PIC X` bytes of a native-byte-order binary (`COMP-5`, or `BINARY-SHORT`/`LONG`/`LONG-LONG`/`DOUBLE`; one-byte `BINARY-CHAR` is skipped); a big-endian `BINARY`/`COMP`/`COMP-4` number over a `POINTER` (the pointer is stored in native byte order, `BINARY`/`COMP` is big-endian by default on every compiler, so on x86 the number is the address byte-swapped; do address arithmetic on the POINTER itself with `SET ptr UP BY`/`TO ADDRESS OF`); and a 4-byte view of a `POINTER` (4 bytes on z/OS with 31-bit addressing, 8 bytes on 64-bit platforms). An 8-byte `PIC X(8)`, `PIC 9(18) COMP-5` or `BINARY-LONG-LONG UNSIGNED` view of a pointer stays clean. An 8-byte `PIC X` view is clean because pointer bytes are never serialized (they only hold an address in memory) and `X(8)` holds an address on every platform, while `X(4)` truncates it on 64-bit. COBOL016 findings can be kept out of a gate with `exclude_types: [COBOL_PLATFORM_DEPENDENT_LAYOUT]` in `.hefesto.yaml` (the issue type name; `COBOL016` itself is not accepted there). **COBOL005** reports one finding per `OCCURS ... DEPENDING ON` entry and skips the CICS `DEPENDING ON EIBCALEN` commarea idiom.
- **COBOL006 / COBOL011 / COBOL015** report repeated findings once (per `PERFORM X THRU Y` pair, per program, per missing copybook), with the occurrence count and lines in the finding metadata.
- **COBOL007 (copybook blast radius)** is reported once on the copybook file when 5 or more scanned programs `COPY` it, directly or through nested copybooks (MEDIUM; HIGH at 15+ programs or for a generic name such as `COMMON`, `UTILS`, `SHARED`). It needs the copybook to be in the scan. **COBOL015 (LOW)** flags a `COPY` whose copybook is not in the scanned tree (also a nested `COPY` inside a copybook); it stays silent when no `COPY` in the scan resolves (for example a single file). Vendor copybooks (CICS `DFH*`, IBM MQ `CMQ*`, DB2 `SQLCA`/`SQLDA`) are skipped by both. `EXEC SQL INCLUDE` members count like `COPY`. Copybooks kept outside the scanned tree resolve with `--copybook-path DIR` (repeatable) or `copybook_paths:` in `.hefesto.yaml`; files there are expanded into the programs that `COPY` them but not analyzed on their own. The search below each copybook path is recursive but bounded: 8 directory levels and 50,000 files (a warning is logged when it stops), hidden directories skipped, and it runs once per run.
- **COPY expansion:** programs are analyzed with each `COPY` (and `EXEC SQL INCLUDE`) replaced by the copybook text, the way the compiler sees it, so every rule sees copybook data definitions, `SELECT`s and procedure code in the context of the program. `COPY ... REPLACING` is applied: `==pseudo-text==` (including an empty replacement), literals, words and identifiers (`A OF B`, `T(1)`), `LEADING`/`TRAILING` partial words, and the `==:TAG:==` / `==(TAG)==` idioms inside words; matching is by text word (case-insensitive words, exact literals, first pair wins, no rescan). A REPLACING also applies to copybooks nested under it. Guards: a copybook already open in the chain is not expanded again (recursion), nesting stops at 16 levels and a program stops expanding after 250,000 copybook lines; a `COPY` that is not expanded stays as written. A finding on copybook text is reported at the program's `COPY` line with the copybook file and line in `metadata.expanded_from`; COBOL004/008/009 on an unchanged line of a scanned copybook stay on the copybook file (not repeated per program), but are reported in the program when `REPLACING` changed that line or the copybook comes from `copybook_paths`. Not supported: the `REPLACE` statement, and `OF library` does not pick between copybooks of the same name (the one closest to the program wins). Copybook files themselves are analyzed as written.
- **COBOL002 (credentials)** skips fields whose name ends in a flag/status/length/label suffix (for example `WS-PASSWORD-OK-FLAG`, `PWD-LEN`).
- **COBOL008-COBOL010 (secrets, CRITICAL)**: a `VALUE` literal on a credential-named field (same suffix exclusions as COBOL002; placeholders such as `SPACES`, `XXXX`, `UNDEFINED` and key names such as `'APP-Token-Password'` are skipped), `PASS=`/`PWD=`/`PASSWORD=` with a value inside any string literal, and `EXEC SQL CONNECT ... USING`/`IDENTIFIED BY` with a literal password.
- **COBOL011 (LOW)** flags `SELECT`s without a `FILE STATUS` clause, one finding per program with the file names in the metadata (sort files declared with `SD` are skipped). **COBOL012 (LOW)** flags an OPENed file whose status field, its subordinates and its 88-levels are never referenced in the PROCEDURE DIVISION (skipped when the status field is not defined in the expanded program, for example in a copybook that was not found, or the PROCEDURE DIVISION has a `COPY` that could not be expanded).
- **COBOL013 (MEDIUM)** flags statements after an unconditional `STOP RUN`/`GOBACK`/`EXIT PROGRAM` in the same paragraph (`EXIT PROGRAM. STOP RUN.` and alternate `ENTRY` points are not flagged). **COBOL014 (LOW)** flags paragraphs and sections that are never referenced (PERFORM, GO TO, THRU ranges, SORT/ALTER) and cannot be reached by fall-through; the entry paragraph, DECLARATIVES, empty `EXIT` paragraphs and programs with a PROCEDURE DIVISION `COPY` that could not be expanded are skipped.
- **Program lineage (`--lineage`, JSON only):** `hefesto analyze --output json --lineage` adds a `lineage` section (`schema_version` 1) with the program graph: `CALL 'X'`, `EXEC CICS LINK`/`XCTL PROGRAM('X')`, `EXEC SQL` tables (from `FROM`, `JOIN`, `UPDATE`, and `INTO` after `INSERT`/`MERGE`, with the statement `op`), and direct `COPY`/`EXEC SQL INCLUDE` edges. Without `--lineage` nothing is extracted and the report is the same as before; with `--output text`, `html` or `sarif` the flag is ignored with a warning on stderr. `nodes` are `program:NAME` (`program:NAME@file` when two files share a name), `copybook:NAME` and `table:NAME`. An edge is created only when a literal target is a program of the scan; there is one edge per (kind, from, to, op, file), with every source line in `lines` (`line` is the first). Other targets go to `references` with `class` `system_service` (`MQ*`, `CEE*`, `DSN*`, `CBLTDLI`, `AIBTDLI`) or `external`. `unresolved` lists what is not followed, with a `reason`: `variable_target` (`CALL WS-PGM`, `PROGRAM(WS-PGM)`), `ambiguous` (name shared by several programs), `dynamic_sql` (`PREPARE`, `EXECUTE`, `DECLARE ... STATEMENT`), `no_program_option` and `copybook_not_copied`. A reference inside a copybook (also one pulled in with `EXEC SQL INCLUDE`) belongs to every program that copies it, directly or through nested copybooks. Variable targets are never guessed. Not covered: `SELECT ... ASSIGN TO` files, `CALL` targets set with `MOVE` or `SET ... TO ENTRY`, tables named only in dynamic SQL, and the `REPLACE` statement. Measured on three public corpora (precision on labelled edges; every literal target is classified once): CardDemo `CALL` 18/18, `XCTL` 2/2, SQL 15/15; GenApp `LINK` 82/82, SQL 33/33; zopeneditor-sample has only `COPY` edges and 3 variable `CALL`s. These are small samples: the 18 CardDemo `CALL` edges go to 2 programs, GenApp is a single application, and CardDemo screen navigation is almost all variable (31 of 33 `XCTL` targets are `PROGRAM(WS-...)`). On those corpora `--lineage` changes the run time by -1 % to +15 % (median of 3). On the synthetic 1,000-program project (1.05M lines, about 60 SQL statements per program) it takes 10.1 s instead of 8.3 s, with peak memory 122 MB instead of 84 MB and a 4.8 MB instead of 3.1 MB JSON; on the single 500,000-line program, 5.7 s instead of 4.9 s. Check the labels with `python scripts/cobol_label_precision.py --lineage carddemo=cd.json --lineage genapp=ga.json --lineage zopeneditor=ze.json`.
- **Measured recall:** 39 of 41 seeded issues (every rule at least twice) are found, including 7 that only fire after COPY expansion; the 2 misses are documented limits: a secret whose value contains a credential word (skipped to avoid placeholder false positives) and a literal that reaches a password field through another field (no data-flow analysis). Run `python scripts/cobol_recall.py`; precision on real corpora is in [docs/cobol-corpus-baseline.md](cobol-corpus-baseline.md).
- **Performance:** about 9 s per million lines on a synthetic 1,000-program project (1.05M lines, nested `COPY` and `COPY ... REPLACING`), about 4.8 s for a single 500,000-line program, with peak memory around 60 MB for the project and 250 MB for the 500k-line file (measured on an 8-vCPU Linux VM with Python 3.13; the analysis is single-threaded). Findings stay grouped, so a 500,000-line file yields 4 findings. Reproduce with `python scripts/cobol_perf_bench.py`.
- Output is text, JSON, HTML or SARIF 2.1.0 (`--format sarif`). In SARIF, a finding on copybook text carries the copybook file and line as a related location. COBOL002 and COBOL003 keep the CWE tags they already set (`external/cwe/cwe-798`, `external/cwe/cwe-20`, no zero-padding); the log also lists that id under `run.taxonomies`. A ready-to-push example repository layout (COBOL app with planted issues and a SARIF workflow) is described in [docs/github-action.md](github-action.md#example-repository).
